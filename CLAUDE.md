# GoldLink — контекст проекта

> Этот файл читается в каждой сессии Claude Code. Держим его компактным и
> актуальным. Детали конкретного модуля даём в задаче, а не тут.

## Что это

Система автоматизации создания спецификаций оборудования и агрегации
проектных материалов для компании GoldLink. Внутри — менеджеры GoldLink;
снаружи — заказчики (представители и сотрудники контрагентов).

## Что мы строим сейчас

**Кликабельный UI-прототип на React.** Цель — интерфейс и навигация всех
модулей на моковых данных. Проверяем UX и ролевую логику, не бэкенд.

### В scope прототипа
Вёрстка и навигация всех модулей, ролевые представления, состояния экранов,
моковые данные, диаграмма Ганта, история версий заявки с diff и откатом.

### Вне scope прототипа (не реализуем, но помним, что это будет)
Аутентификация (Keycloak / Active Directory / федерация / SSO / фоллбэк),
парсеры вендоров, объектное хранилище S3, email-уведомления, реальный бэкенд
и БД. Роль в прототипе переключаем моком (селектор роли), без реальной авторизации.

## Стек
- React.
- UI-kit: **УТОЧНИТЬ** (решение за пользователем).
- Диаграмма Ганта: в прототипе — **верстанный интерактивный мокап без внешней
  библиотеки** (бары считаются из дат, клики/тултипы/панели работают). На этапе
  реализации предполагается библиотека [svar.dev](https://svar.dev/)
  ([демо](https://svar.dev/demos/react/gantt/)) — её кастомизация ограничена.
  Что НЕ делаем в прототипе (помечаем заглушкой «на этапе реализации — библиотека»):
  drag-and-drop баров, авто-пересчёт дат по зависимостям, линии критического пути.

## Доменная модель

Иерархия (жёсткая, вся ролевая логика висит на ней):

```
Заказчик (юрлицо: название, ИНН, контакты, адрес)
└── Объект (шахта/ГОК/фабрика: название, описание, локация, геопозиция)
    ├── Служба (только название)
    │   └── Представитель заказчика (1..N)
    ├── Материалы → Файлы
    ├── Этапы работ (диаграмма Ганта)
    └── Заявки
Заказчик
└── Сотрудник заказчика (0..N) — без привязки к объекту/службе
```

Каталог отдельной веткой: `Вендор → Товар` (товары приходят парсингом,
**в интерфейсе не редактируются**).

Ключевые сущности: Заказчик, Объект, Служба, Представитель_заказчика,
Сотрудник_заказчика, Менеджер GoldLink, Товар, Заявка, Версия_заявки,
Материал, Файл, Этап_работ, Справочная_статья, Вендор.

### Инварианты модели (обязательны в UI)
- Представитель **всегда** привязан ровно к одной службе. Через неё
  автоматически определяются его объект и заказчик.
- При создании заявки объект/служба/заказчик **не выбираются вручную** —
  подставляются из профиля представителя.
- Сотрудник заказчика не привязан к службе/объекту → не создаёт заявки,
  не видит объекты/этапы/материалы/заявки. Каталог — только просмотр.
- Скоуп представителя фильтруется на уровне **датасета**, а не отображения:
  он физически не видит чужих заказчиков/объектов/служб нигде.
- Удаление невозможно при наличии связей: службу — с представителями/заявками;
  объект — со службами/материалами/этапами; заказчика — с объектами/сотрудниками/
  представителями. Каскадного удаления нет.

## Роли и матрица доступа

Три роли: **Сотрудник заказчика**, **Представитель заказчика**, **Менеджер GoldLink**.

| Функция | Сотрудник | Представитель | Менеджер |
|---|---|---|---|
| Каталог: просмотр/поиск | да (только просмотр) | да | да |
| Каталог: корзина / заявка | — | да | — |
| Каталог: тех. статистика | — | — | да |
| Заявки: просмотр | — | свои | все |
| Заявки: редакт. состава | — | до статуса «Исполнена» | да |
| Заявки: смена статуса / загрузка док. | — | — | да |
| Заявки: экспорт .xlsx / история | — | да | да |
| Объекты: просмотр / скачивание файлов | — | свой объект | все |
| Объекты: структура (объект, службы) | — | — | только в «Управлении» |
| Объекты: контент (материалы) в карточке | — | просмотр/скачивание | CRUD |
| Гант: просмотр | — | свой объект | все |
| Гант: создание/редактирование | — | частично¹ | да |
| Обучающие материалы: просмотр | да | да | да |
| Обучающие материалы: создание | — | — | да |
| Управление (весь каскад сущностей) | — | — | да² |

¹ Представитель правит: описание, статус, % выполнения, ответственного.
Даты этапа — только через менеджера (вне системы). Drag-and-drop дат — только менеджер.
² В прототипе — полный функционал модуля (это фоллбэк-режим; при AD часть уходит в каталог).

## Модули

### 1. Каталог
Товары из выгрузок вендоров (парсинг — вне прототипа, данные мокаем).
Карточка товара: наименование, артикул, вендор (виден только Менеджер), категория, тех. параметры.
**Не показывает** цены, остатки, коммерческие условия.
Поиск: полнотекстовый (наименование/артикул/описание/характеристики) +
навигация по иерархии категорий. Фильтры по характеристикам — **отложены**
(структура зависит от данных вендоров), но верстаем с заделом на расширение.
Корзина → «Сформировать заявку»: количество/удаление позиций, авто-атрибуция,
номер формата `GL-YYYY-NNNN`, генерация первичной спецификации `.xlsx`.
Управление вендорами — в зоне Каталога (только менеджер).

### 2. Заявки
Статусы: `сформирована → в работе → исполнена`.
Состав редактируется представителем (своя служба) и менеджером **до «Исполнена»**,
дальше блок. Редактирование состава идёт через полноценный каталог+корзину на
отдельном маршруте `/orders/:id/edit` (корзина предзаполнена текущим составом,
«Сохранить» перезаписывает состав редактируемой заявки). Версионирование:
каждое сохранение состава — новая версия с датой, автором и дельтой
(добавлено/удалено/изменённое количество). Карточка заявки → «История изменений»
с diff между версиями и откатом (откат = новая версия «восстановлено из версии N»).
Экспорт текущего состава в `.xlsx`. Смена статуса — только менеджер. Документы:
прикрепление/удаление — менеджер (доступно в любом статусе, включая «Исполнена»),
скачивание — обе роли. Удаления заявки нет (архив через статус).

### 3. Объекты
Список объектов и карточка объекта — **только просмотр структуры**. Создание и
редактирование объекта и служб — в модуле «Управление», не здесь.
В карточке объекта **редактируется только контент**: материалы и план работ (Гант).
- **Материалы:** менеджер — CRUD записей + мультизагрузка файлов; представитель —
  просмотр/поиск/скачивание по своему объекту. Скачивание файлов — обе роли,
  загрузка/удаление — менеджер. Файлы держим как Blob в памяти (мок в пределах сессии).
- **Службы:** в карточке объекта **показываются только для просмотра**; CRUD — в «Управлении».
- **Гант (верстанный мокап, без библиотеки):** этап = название, описание, даты,
  статус (`запланирован/в работе/выполнен/отложен`), ответственный, привязанные
  файлы, зависимость_от (self-ref), % выполнения. Десктоп — бары на шкале
  (позиция/ширина из дат), цвет по статусу. % выполнения правится ползунком прямо
  на баре (и в панели этапа), сохранение сразу. Клик по этапу → **единая боковая
  панель, сразу редактируемая, БЕЗ кнопок «Редактировать»/«Сохранить»/«Отмена»**:
  автосохранение на лету (текстовые поля — по blur, селекты и ползунок — сразу),
  закрытие панели ничего не теряет. Редактируемость полей по роли (менеджер — все;
  представитель — только описание, статус, %, ответственный; статус «Исполнена» и
  мобильный — всё read-only). Удаление этапа — исключение: кнопка с подтверждением.
  «Добавить этап» — отдельной кнопкой (менеджер).
  Мобильный — упрощённый список этапов, без редактирования, для всех ролей.
- **Гео:** кнопка «Смотреть на карте» → Яндекс.Карты в новой вкладке.

### 4. Обучающие материалы (справочные статьи)
Статья: название, дата, rich-text (текст + изображения + embed-видео Rutube).
Просмотр — всем; CRUD — только менеджер. Полнотекстовый поиск.

### 5. Управление (менеджер)
**Единственное место создания/редактирования всего каскада сущностей:**
Заказчик → Объект → Служба → Представитель / Сотрудник, сверху вниз в одном потоке
(создал заказчика → внутри объект → внутри службу → внутри представителя, не
прыгая между модулями).
Заказчик: название, контактное лицо, email (обяз.) + ИНН, телефон, адрес,
комментарий. Объект: название, привязка к заказчику + описание, локация,
геопозиция, дата начала. Служба: название (объект/заказчик из контекста).
Представитель: логин, email, **привязка к службе** (обяз.) + ФИО/телефон/должность;
привязку к службе после создания не меняем. Сотрудник: то же, но **привязка к
заказчику** (без объекта/службы). Уникальность логина — глобальная по всем ролям.
Деструктив — через модалку. Списки объектов и карточка объекта тянут данные отсюда.

## UI-соглашения (общие)

- **Один общий app shell**: единый сайдбар + роутинг на всё приложение.
  Модуль НЕ тащит свою навигацию. Все модули живут в одной оболочке.
- Справочники произвольной мощности (заказчик/объект/служба, категории) →
  **каскадные фильтры**, а не фиксированные списки.
- Фиксированные наборы (статусы) → сегментированные пилюли с цветовой индикацией.
- Добавление позиций → каталог-корзина; данные позиции берутся из записи товара.
- История версий → панель с дельтами, откат к версии, экспорт в `.xlsx`.
- Хлебные крошки для навигации по иерархии; отдельная кнопка «назад» не нужна.
- Роль в прототипе → переключатель (мок), меняет и меню, и датасет.
- Адаптивность: клиентская часть (каталог, заявки, объекты, материалы,
  просмотр Ганта) — адаптивная; **админ-панель менеджера** (импорт, «Управление»,
  редактирование Ганта) — только десктоп.
- **«Управление»** — единственное место создания/редактирования каскада
  Заказчик → Объект → Служба → Представитель/Сотрудник. Больше нигде эти сущности
  не создаются. Список объектов и карточка объекта — только просмотр структуры;
  редактируется там лишь контент (материалы, Гант).
- Управление вендорами — в зоне Каталога (только менеджер).
- Поле «Вендор» скрыто от представителя и сотрудника везде: и в карточке товара
  каталога, и в составе заявки. Видит только менеджер.
- Заказчик очень ценит визуальную составляющую и графику. Где уместно —
  предпочитать карточки с изображениями/превью «сухим» таблицам; закладывать
  место под картинки (обложки, превью, иконки-плейсхолдеры). Касается всех модулей.
- «Карточки с картинками» применять к спискам-витринам (список объектов, каталог),
  а не автоматически ко всем вложенным сущностям. Внутренние списки (файлы, позиции)
  остаются компактными строками, если не сказано иное.
- Inline-редактирование без кнопки «Сохранить» (как в панели этапа Ганта):
  текстовые поля сохраняются по потере фокуса, селекты/ползунки — сразу; закрытие
  ничего не теряет. Деструктив (удаление) — всегда с подтверждением, не автосейвом.

## Дизайн-правила (обязательны — из разбора прошлых итераций)

1. Не хардкодить длину списков фильтров/тегов — число значений произвольно
   и приходит с бэкенда; учитывать переполнение (особенно в шапке).
2. Не дублировать навигацию (крошки vs кнопка «назад»).
3. Один сайдбар и роутинг на приложение; модуль не приносит свою навигацию.
4. Сначала понять, что строим (данные, роли, состояния), потом расставлять UI.
5. Любые данные считать переменной длины — не подгонять вёрстку под демо-данные.

## Интеграционный проход (запланирован — сразу после модуля «Управление»)

«Управление» собирается ближе к концу, хотя по данным оно фундаментальное. Поэтому
после него — отдельный интеграционный проход одной серией, не размазывая по модулям:
- **Единый стор сущностей:** все модули читают заказчиков/объекты/службы/
  пользователей из общего источника («Управление»), а не из локальных моков.
  Пройти по местам использования: фильтры и привязки в «Заявках», списки в
  «Объектах», все выпадашки выбора заказчика/объекта/службы.
- **«Объекты» → режим просмотра:** убрать редактирование объекта, службы — только
  показ, данные тянуть из «Управления» (см. UI-соглашения).
- **Консистентность имён:** заказчики/объекты/службы во всех модулях совпадают
  с «Управлением» (сейчас местами расходятся от сессии к сессии).
- **Проверка по всем трём ролям** после переключения на единый стор.

Каталог, механику заявок, Гант и обучающие материалы внутренне это не затрагивает.

## Возможные будущие изменения
- Право менеджера редактировать состав заявки: сейчас есть (по ТЗ 4.2.2 / 3.3),
  вероятно будет убрано — состав правит только представитель.
- Редактирование заявки с товаром, отсутствующим в текущем каталоге: не обработано,
  открытый вопрос.
- **Представитель НЕ редактирует поля объекта** — правка объекта только у менеджера
  в «Управлении». Отклонение от ТЗ 4.3.3 (давал представителю правку названия/
  описания/локации). Принято нами, **ТРЕБУЕТ СОГЛАСОВАНИЯ с заказчиком.**
- Возможный уровень «Проект»: список проектов → карточка проекта → план работ
  (сейчас этапы висят прямо на объекте). В ТЗ сущности «Проект» нет — кандидат на
  расширение за отдельную оплату.
- Drag-and-drop баров Ганта (перенос дат перетаскиванием) — не реализован в
  прототипе, на этапе реализации через библиотеку.
- Заведение менеджеров GoldLink: на прототипе доступно менеджеру (раздел «Сотрудники GoldLink» в «Управлении»). Это админская по смыслу функция — кандидат на вынос под отдельную роль «Администратор» (в ТЗ такой роли нет). Обсудить с заказчиком: нужна ли роль «Админ» над менеджером.

## Открытые вопросы (из ТЗ, раздел 8 — решаются заказчиком, не выдумывать)

Не приняты и не должны «додумываться» в прототипе:
- Итоговое размещение (облако vs контур GoldLink) и схема аутентификации.
- Детальная структура фильтров каталога (зависит от данных вендоров).
- Название третьей роли (сотрудник/наблюдатель/аналитик) — на согласовании.
- MFA, политика паролей, схема маппинга AD — вне прототипа.
- Целевые показатели нагрузки — не заданы.

Если по ходу прототипа всплывает пункт отсюда — не решаем молча, помечаем как вопрос.
